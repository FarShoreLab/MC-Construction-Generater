## 用户目标与边界

现有项目希望在不升级基模、不增加大量模型调用的条件下，提高地形自适应聚落的规划质量和建筑需求满足能力。上一轮建议“用途、地块、道路相互协调”过于抽象。本次必须把它落实成可编译、可测、有明确成本上限的工程实现。

本次主任务是聚落规划重做，包括用途分配、建筑尺寸需求、地块选择、道路与入口连接、地基土方及调用链集成。不要顺手重写所有单体建筑生成器或 GUI。已有 Python 建筑生成实验仅作为背景，不是必须迁移到 Java 的系统。

允许替换规划算法，不要求沿用某个预设方案。你必须根据实际代码选择最小可行设计，并说明为什么它比原实现更好。不预设联合求解、WFC、多智能体或大而全的优化框架必然有用。

## 需要你核实的问题，不要未经检查就照单实施

- 现有规划是否固定入口、广场、山脊、回环，再按道路遍历顺序贪心塞地块？哪些需求实际无法影响结果？
- landmarkPlacement 等字段是否传到最终求解器？模型得到的地形信息是否足够？
- 固定地块尺寸、建筑旋转和预设裁剪是否冲突？地块用途能否覆盖全局提示词关键词，避免所有房子变成铁匠铺？
- A* 的中心线、道路实际宽度、对角移动、高差、桥梁和施工后的可通行性是否一致？标记 stair 不等于实际能走。
- 地基最大挖深/填高是否是逐格硬约束？无可行标高时是否被误报成成功？
- 路网拓扑中的路口节点与实际相交道路是否一致？每个地块是否存在从真实门口到道路的合法接入路径？
- 现有分数是否偏好大量但平衡的挖填？是否掩盖用途缺失、断路、不可施工的问题？

## 工程要求

- 保持 Java 21 和 core-planner 不依赖 Minecraft 的边界。优先复用现有组件；新依赖必须有必要性。
- 核心几何规划和测试无需联网或调用 LLM。低成本模型可以输出有界的结构化需求，不能依赖它逐个猜坐标、逐层生成方块或自评打分。
- 为用途、数量、尺寸范围和必要空间关系建立最小需求表达。支持旧调用方合理默认值；新增字段必须真正被生产调用链使用。
- 明确硬约束、候选生成方式、选择/改进操作、终止条件、复杂度与预算。不要只说“多目标优化”或“迭代改进”。如使用评分，给出各项单位、归一化、权重依据；硬约束不允许被高分抵消。
- 同一地图、需求、seed 和搜索预算产生相同几何结果，时间戳等非几何元数据除外。搜索次数要有上限；耗时需实测，不能宣称未经测试的毫秒级性能。
- 无可行解或只能满足部分需求时返回明确状态、未满足项目和原因。不要静默少建后宣称成功，不允许降级结果违反硬约束。
- 建筑占地、门口、道路宽度、地基和施工消费者应使用一致的坐标约定。新增 IR 字段需要同步处理必要的消费者。
- 改动范围只覆盖本任务及其必要集成；不改变密钥配置、不调用收费 API、不做无关格式化。
